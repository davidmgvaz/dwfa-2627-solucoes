# Ficha 04 — perguntas de reflexão · reflection questions

**1. O *guard* `beforeEach` impede um utilizador sem sessão de ver `/orders`. Um utilizador curioso abre as DevTools e remove o *guard* (ou chama a API com `curl`). O que vê? Expliquem o que protege de facto os dados e porque é que o *guard* existe na mesma.**

PT — Vê o ecrã `/orders` a carregar e, logo a seguir, o estado de erro: a API responde `401` (sem `Bearer`) ou, com o token de outro cliente, devolve só as encomendas **desse** cliente — e `404` para as alheias (Ficha 03). Com `curl` é igual: sem token `401`, com token só o que é seu. O que protege os dados é a API — `JWTAuthentication`, `IsAuthenticated`, `IsOwnerOrGestor` e o `get_queryset` filtrado — porque corre num sítio que o utilizador não controla. O *guard* corre no browser do utilizador, que pode alterar tudo; não é segurança, é **experiência**: evita mostrar ecrãs vazios com erros `401`, leva para o login e volta ao sítio certo (`?next=`). Regra: o cliente decide o que *mostra*; o servidor decide o que *existe*.

EN — They see `/orders` load and then the error state: the API answers `401` (no `Bearer`) or, with another customer's token, returns only **that** customer's orders — and `404` for anyone else's (Ficha 03). `curl` behaves the same. What protects the data is the API — `JWTAuthentication`, `IsAuthenticated`, `IsOwnerOrGestor` and the filtered `get_queryset` — because it runs where the user has no control. The guard runs in the user's browser, which they fully control; it is not security, it is **UX**: no blank screens with `401`s, a redirect to login and back (`?next=`). Rule: the client decides what it *shows*; the server decides what *exists*.

**2. O `price` chega à SPA como `string` (`"9.90"`). Porque é que o DRF serializa `DecimalField` assim, o que corre mal se o converterem para `number` para somar o total de uma encomenda, e onde é que a aritmética de dinheiro deve viver?**

PT — O JSON só tem um tipo numérico, o *double* IEEE 754 do JavaScript: `0.1 + 0.2 = 0.30000000000000004`, e `9.90` não tem representação exata. O DRF (`COERCE_DECIMAL_TO_STRING = True`) serializa `Decimal` como *string* para o valor chegar **intacto** ao cliente, sem arredondamentos pelo caminho. Converter para `number` para somar é aceitável para *mostrar* uma estimativa (`Intl.NumberFormat` arredonda a 2 casas) mas não para decidir nada: somar 40 linhas de `19.99` em *double* dá `799.5999999999999`, e com quantidades e descontos o erro acumula-se e pode diferir do total que a API calcula. A aritmética de dinheiro vive no servidor — `Decimal`/`NUMERIC(12,2)` no PostgreSQL, `Sum(F("quantity") * F("unit_price"))` — que é também o único sítio em que o preço unitário é confiável (`unit_price` copiado do produto no `create`, nunca vindo do cliente). O cliente mostra o `total` que a API devolve; se precisasse de aritmética exata no browser, usaria cêntimos inteiros ou uma biblioteca de decimais (`decimal.js`, `Big.js`).

EN — JSON has a single number type, JavaScript's IEEE 754 double: `0.1 + 0.2 = 0.30000000000000004`, and `9.90` has no exact representation. DRF (`COERCE_DECIMAL_TO_STRING = True`) serialises `Decimal` as a string so the value reaches the client **intact**. Converting to `number` is fine to *display* an estimate (`Intl.NumberFormat` rounds to 2 places) but not to decide anything: 40 lines of `19.99` summed as doubles give `799.5999999999999`, and with quantities and discounts the error compounds and may differ from the API's total. Money arithmetic lives on the server — `Decimal`/`NUMERIC(12,2)` in PostgreSQL, `Sum(F("quantity") * F("unit_price"))` — which is also the only place where the unit price is trustworthy (`unit_price` copied from the product on `create`, never from the client). The client shows the `total` the API returns; if it ever needed exact arithmetic in the browser it would use integer cents or a decimal library.
